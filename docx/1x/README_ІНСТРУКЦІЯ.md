# Інструкція з оновлення та імпорту виправлених модулів VBA

Папка: `d:\GitHub\47\VBA_Fixed\`

Усі файли перевірені та збережені у стандартному для Excel VBA кодуванні **Windows-1251 (CP1251)** з обов'язковими для компілятора Windows перенесеннями рядків **CRLF** (без "битих" символів чи знаків питання).

## 🔴 Чому в «Додатку 47» виникала помилка `quantity = filteredData(n, 7)` та що виправлено

При формуванні аркуша **«Додаток 47»** макрос зупинявся з помилкою:
> **Run-time error '13': Type mismatch** на рядку `quantity = filteredData(n, 7)`

### Корінь проблеми:
1. **Порожнє значення в стовпчику 7 (G «Вибуло»)**:
   Масив `filteredData` зчитувався з клітинок Excel як текст (`cell.Cells(1, j).text`). 
   Коли в базі траплялася операція повернення майна з підрозділу на склад (або переміщення, де кількість внесена у стовпчик F «Надійшло»), у стовпчику G було пусто (`""`).
   Спроба присвоїти порожній текстовий рядок змінній `Dim quantity As Double` викликала миттєве аварійне падіння VBA з помилкою 13 (Невідповідність типу).
2. **Знищене/списане майно тягнуло у підрозділи та завищувало залишки**:
   Коли майно списувалося або знищувалося (стовпчик I «Куди» = «Списання»), старий макрос сприймав «Списання» як окремий бойовий підрозділ! Він створював стовпчик «Списання» і додавав туди списане майно за 5-ю категорією. У кінці звіту `SUMIFS` підсумовував усі стовпчики підрозділів, включаючи «Списання», тому знищене майно продовжувало рахуватися як діюче наявне майно військової частини.
3. **Відсутність хронологічного сортування**:
   У таблиці «База» рядки розташовані в порядку їх внесення оператором, а не за датою документів. Старий макрос обробляв операції хаотично (наприклад, видача в підрозділ могла оброблятися раніше, ніж початкове надходження з центру забезпечення), що створювало фіктивні мінусові залишки та порушувало форму 47.
4. **Збій номерів категорій (`wsAdd47.Cells.Find`)**:
   Для пошуку стовпчика потрібної категорії макрос викликав глобальний пошук `Cells.Find(What:=CategoryTo)`. Оскільки рядок 19 містить наскрізну нумерацію стовпчиків (1, 2, 3, 4, 5...), а також інші підрозділи мають такі ж цифри, функція `Find` перескакувала на довільні стовпчики або номери колонок, записуючи кількість не в ту категорію.

### Як це виправлено в `Add47.bas`:
- **Безпечне зчитування кількості (`SafeVal`)**: створено універсальну функцію парсингу чисел, яка враховує пробіли, коми, крапки та нерозривні пробіли. Якщо стовпчик 7 порожній, кількість автоматично зчитується зі стовпчика 6 (і навпаки). Помилка 13 повністю виключена.
- **Хронологічне сортування (`SortFilteredData`)**: перед формуванням таблиці масив транзакцій сортується за алгоритмом QuickSort: **спочатку за датою документа / роком (стовпчик 13 / 1), потім за номером документа (стовпчик 14)**.
- **Правильна обробка «Списання» / знищеного майна (`IsWrittenOffUnit`)**:
  - «Списання» чи «Знищено» більше **ніколи не створює колонку підрозділу**!
  - Кількість записується у стовпчик G («Вибуло») як факт списання.
  - Кількість списується з відправника (`FromUnit`) та вираховується із загального залишку військової частини.
  - Знищене майно більше не з'являється у діючих залишках (стовпчик 8).
- **Математична адресація категорій без `Find`**: кожен підрозділ займає строго фіксований блок із 6 колонок (`uCol` — Усього, `uCol + 1` — Кат 1, `uCol + 2` — Кат 2, ..., `uCol + 5` — Кат 5). Звернення до категорії виконується миттєво через прямий зсув `uCol + cat`.
- **Розумне списання (`DeductFromUnit`)**: якщо в рапорті на списання вказано 5 категорію, а майно в підрозділі обліковувалося за 2 або 1 категорією, макрос списує майно з тієї категорії, де воно фактично є, уникаючи мінусів.

## 🔴 Чому інвентаризація формувала пустий шаблон і що виправлено

При формуванні «Інвентаризаційного опису» або «Інвентаризаційного опису НА» створювався повністю порожній документ (шаблон без жодного рядка майна).

### Причини проблеми:
1. **Жорсткий фільтр за субрахунком**:
   У версії 3.9.27 розробник додав перевірку: макрос брав субрахунок зі стовпчика X («Поле 12») аркуша «База» і шукав його у списку дозволених субрахунків (1014, 1113 тощо).
   У базі стовпчик X виявився порожнім для 100% рядків! Макрос відкидав абсолютно всі рядки (`GoTo NextRow`).
2. **Внутрішнє переміщення / повернення**:
   Макрос перевіряв кількість лише у стовпчику G («Вибуло»). Повернення майна у стовпчику F («Надійшло») губилося.
3. **Дата інвентаризації**:
   Дата документа не зіставлялася коректно з датою зрізу інвентаризації (`invAsOf`).

### Як це виправлено:
- **Автоматичне підставлення субрахунку**: якщо в базі стовпчик X ще не заповнений, макрос автоматично відносить майно до типового субрахунку (`1113` для «Основних засобів / НА» або `1812` для «Запасів»). Усі 64+ найменування (РЕБ, купольні комплекси тощо) тепер миттєво підтягуються в опис!
- Кількість переміщення зчитується з обох колонок (F та G).
- Враховується дата зрізу інвентаризації (`invAsOf`).

## 🛠️ Покрокова інструкція з імпорту в Excel

1. Відкрийте файл книги **«База даних Накладних 3.9.28.xlsm»** в Excel.
2. Натисніть **`Alt + F11`** (відкриється редактор VBA).
3. У панелі **Project Explorer** (зліва) знайдіть папку **Modules**.
4. **Для кожного потрібного модуля** (наприклад, `Add47`, `Inventory`, `InvertoryNonCurrentAssets`):
   - Клікніть правою кнопкою миші на старий модуль (наприклад, `Add47`).
   - Виберіть пункт **Remove Add47...** ➔ натисніть **No** (Ні, не експортувати).
   - Натисніть **`Ctrl + M`** (або через меню: File ➔ Import File...).
   - У вікні виберіть оновлений файл із папки `d:\GitHub\47\VBA_Fixed\` (наприклад, `Add47.bas`).
5. Перевірте проект: меню **Debug ➔ Compile VBAProject**.
6. Збережіть книгу (**`Ctrl + S`**).
7. Запустіть формування Додатка 47 або Інвентаризації — документи сформуються без помилок та з точними залишками!
